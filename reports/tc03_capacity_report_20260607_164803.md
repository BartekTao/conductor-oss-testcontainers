# TC03 Capacity Report - Preloaded Independent Poll Scaling

## Summary

本輪 TC03 用 TC01 的單 queue SLA candidate 40 completed task/s 作為 baseline，觀察多 workflow/task pair 在 preloaded backlog 下是否能線性擴展。結果顯示：**本機環境下 1 pair x 40 RPS 可作為 SLA candidate；2 pairs 起雖然沒有 poll/complete error，但 latency 進入秒級，不應宣告為 500ms 級 SLA。**

若只看功能吞吐而不套用 500ms latency guardrail，最高觀察到的可用點是 **2 pairs x 40 RPS**，實際完成約 71.7 tasks/s，scaling efficiency 0.896。但這些多 pair 結果的 poll/update p95 已超過 500ms，因此只能列為容量上限觀察，不是 SLA。

## SLA Candidate

- 建議短跑產品規格：**TC03 多 pair 場景暫不宣告超過 1 pair x 40 RPS 的 500ms SLA**。
- 可宣告條件：`errors == 0`、每個 active pair 都 stable、`dropped_iterations == 0`、`scaling_efficiency >= 0.85`、`poll_attempt_latency p95 <= 500ms`、`task_update_latency p95 <= 500ms`。
- 2 pairs x 40 RPS 的 efficiency 仍有 0.896，但 poll p95 2452.6 ms，不能當低延遲 SLA。

## Experiment Method

每輪先建立 `MAX_PAIR_COUNT=4` 的 definition，對 active pairs preload workflow backlog。正式階段只啟動每個 pair 自己的 worker scenario，各自以 `PAIR_POLL_RPS` 做 `poll -> complete`。測試分成兩組：以 TC01 40 RPS baseline 做 scaling cliff 掃描，以及降低到 20 RPS/pair 的補充觀察。

## Capacity Sweep

## Interpretation

1 pair x 40 RPS 幾乎線性達標，poll p95 只有 9.3 ms。2 pairs x 40 RPS 開始出現明顯排隊，雖然功能成功率仍為 100%，但 p95 已不可接受。4 pairs x 40 RPS 是明確 cliff，efficiency 掉到 0.685，且 hit max VUs。20 RPS/pair 的補充組證明降低 per-pair RPS 可改善 throughput ratio，但 latency 仍超過 500ms guardrail。
