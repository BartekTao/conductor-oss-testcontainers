## Method

測試分成兩個階段：

```text
setup:
  create / validate pair 001 definitions
  create / validate pair 002 definitions
  preload 4 workflow instances per pair

runtime:
  worker_pair_001 polls task type 001 at 1 RPS
  worker_pair_002 polls task type 002 at 1 RPS
  each poll hit is completed immediately
```

本次每組 preload 4 個 workflow instances，高於 3 秒測試期間的預期 poll 次數，目的是避免 backlog 提早被 drain 完造成 poll miss。

## Observations

兩組 pair 都完成 3 次 task poll/complete，沒有 poll miss，也沒有 complete error。這代表在本次小流量設定下，不同 task type 的 worker scenario 可以並行 consume 各自的 preloaded backlog。

`scaling_efficiency = 1.00`，表示實際完成 RPS 與本次設定的 baseline 一致。這是 smoke-level scaling 驗證，不表示高 RPS 下仍會維持線性擴展。

`poll_attempt_latency p95` 出現約 1 秒的高值。因為本次測試 duration 很短、樣本數只有 6，單一較慢 poll 會大幅影響 p90/p95。若要判斷是否為穩定現象，需要用較長 duration 與更多樣本重跑。

`task_scheduled_to_poll_latency` 約 2-4 秒，符合 preload 模型：workflow instances 先被建立，task 在 queue 中等待 worker 以固定 RPS 逐步消化。

## Limitations

本次只啟用 2 組 pair、每組 1 RPS、測試 3 秒，結果只代表 TC03 腳本與 multi-pair preload/poll/complete 流程可用。容量評估仍需要依 spec 使用 `PAIR_COUNT=1,2,4,8,16` 與較長 duration 逐輪測試。
