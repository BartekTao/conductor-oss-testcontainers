# TC01 Capacity Report - Preloaded Workflow Poll Task

## Summary

本輪測試目標是找出單一 preloaded workflow/task queue 的 `poll -> complete` 可承受上限，測試期間不計入 workflow create throughput。以本機 Conductor + MariaDB Queue 環境、15s 短跑容量掃描來看，**可作為短跑 SLA candidate 的最大點是 40 poll RPS**。在這個點，completed task RPS 約 40.1，poll p95 279.3 ms，task update p95 26.1 ms，沒有 dropped iterations、poll errors 或 complete errors。

功能上限高於 SLA 上限：60 RPS 仍可完成主要工作，但 latency 或 dropped iterations 已不適合宣告為產品 SLA。第一個明確 cliff 出現在 50 RPS 附近。

## SLA Candidate

- 建議短跑產品規格：**TC01 單 queue poll/complete 40 RPS**。
- SLA guardrail：`poll_attempt_latency p95 <= 500ms`、`task_update_latency p95 <= 500ms`、`dropped_iterations == 0`、`errors == 0`、`poll_miss_ratio == 0`。
- 這份結果是本機 15s capacity sweep，適合作為初版產品規格候選值；正式 SLA 仍需要在目標部署規格上跑 10-30 分鐘 soak confirmation。

## Experiment Method

每輪先建立獨立 workflow/task definition，再 preload 足夠 workflow backlog，preload 數量約為 `POLL_RPS * 15s * 1.5`。正式測試階段只執行 worker `poll -> complete`，並用 k6 `constant-arrival-rate` 固定輸入 RPS。

## Capacity Sweep

| Target RPS | Preload | Completed / Expected | Achieved RPS | Dropped | Poll p95 ms | Complete p95 ms | SLA Pass |
|---:|---:|---:|---:|---:|---:|---:|:---:|
| 20 | 450 | 301/300 | 20.1 | 0 | 27.4 | 43.6 | PASS |
| 40 | 900 | 601/600 | 40.1 | 0 | 279.3 | 26.1 | PASS |
| 50 | 1125 | 719/750 | 47.9 | 31 | 822.7 | 1143.0 | FAIL |
| 60 | 1350 | 900/900 | 60.0 | 0 | 651.5 | 48.6 | FAIL |
| 75 | 1688 | 1030/1125 | 68.7 | 96 | 1876.2 | 2215.9 | FAIL |
| 100 | 2250 | 1172/1500 | 78.1 | 329 | 3875.0 | 3333.7 | FAIL |

## Interpretation

20/40 RPS 都滿足 SLA guardrail；40 RPS 是目前最大合格點。50 RPS 和 75/100 RPS 有 dropped iterations 或秒級 latency，不應寫成 SLA。60 RPS 在本輪吞吐達標但 poll p95 為 651.5 ms，超過 500ms guardrail，因此只能列為功能容量觀察值，不列入 SLA。
